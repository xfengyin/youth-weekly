## 刊首语

你有没有过这种时刻：装了一堆效率工具，结果每天花在「整理工具」上的时间比省下来的还多？

这期我们想聊一个反直觉的话题：效率不是「又装了一个新工具」，而是「把手上这套工具链的每一环都调顺」。我见过效率最高的开发者，工具单往往很短——一个顺手的终端、一份维护了三年的 dotfiles、一套跑起来就再也不用管的自动化。真正值钱的不是工具本身，而是围绕工具沉淀下来的流程和习惯。

所以这一期，我们不讲「本月必装清单」，只给三件这周就能做完的基建小事：把终端调顺、把重复劳动写成脚本、给工具链做一次「年度体检」。做完这三件，你会发现效率不是加法，而是减法。

你的工具链里，最该被「淘汰」的那个工具是什么？

## 科技新势力

### 构建提速：从 5 分钟到 40 秒的三种做法

本周社区讨论集中在一件事：构建太慢。三种被反复验证的做法是：增量编译（只重建改动过的部分）、缓存依赖层（把不变的内容提前打包）、以及并行任务（把互相独立的步骤同时跑）。三者叠加，常见项目都能把构建时间压到原来的十分之一。

为什么值得关心：构建时间不只是「等待」，它打断心流。一次 5 分钟的构建等于一次注意力的强制迁移，一天十次，就是每天一小时的隐形损耗。

你现在能做什么：先给你的项目做一次「构建时间画像」——记录哪一步最慢；然后只做一件事：把最慢的那一步缓存起来，本周就能见效。

### 本地模型推理框架：显存不够也能跑

本周开源的推理框架又往前走了一步：通过量化与内存复用，8GB 显存也能跑此前需要 16GB 的模型。对普通用户，这意味着「本地跑模型」从折腾变成日常——离线、隐私、无限制次数，都是云端方案给不了的。

为什么值得关心：本地推理的成本正在快速逼近「免费」，而它在隐私和离线场景的优势是结构性的。工具链里放一个本地模型，等于给自己留了一条不依赖网络的退路。

你现在能做什么：为你最常用的一个场景（翻译、摘要、代码补全）选一个本地模型，跑通一次；把命令存进 dotfiles，下次换机器十分钟恢复。

### 终端的新生：从「黑框框」到「生产力入口」

终端工具这一周又热闹起来：新的 TUI 框架、更好的模糊搜索、以及把终端当「控制台」用的工作流。终端之所以还值得投入时间，是因为它是少数「文本进、文本出、可脚本化」的界面——你的所有操作都能被记录、复用、自动化。

为什么值得关心：图形界面适合「人操作」，终端适合「人设计、机器重复」。把高频操作搬进终端，是让「个人生产力」可复制、可迁移的第一步。

你现在能做什么：挑一个你每周做三次以上的图形界面操作（比如改配置、查日志），看看有没有对应的终端命令；有，就写进你的笔记，攒够五个，你就有了一份自己的「终端速查表」。

## 好工具

### dotfiles 不是玄学：一份可复制的配置仓库

把终端、编辑器、git 的配置收进一个 git 仓库，就是 dotfiles 的雏形。它解决的真问题是「换机器成本」：新电脑从零配环境要半天，有了 dotfiles 只要十分钟加一条安装脚本。

为什么值得关心：配置即资产。你积累的别名、快捷键、插件组合，本质上是你「工作方式的源代码」——放在仓库里，才不会被一次格式化硬盘带走。

你现在能做什么：今天就把 `.bashrc`、编辑器配置、git config 收进一个仓库，加一份 README 说明每个文件是干嘛的；不需要一步到位，先「收进去」就赢了。

### 把重复劳动写成脚本：三个常见场景

三个最容易自动化、也最容易被忽略的场景：批量改名（文件/分支/标签）、重复填表（固定的模板文本）、定时提醒（每周要做的琐事）。每个场景的脚本都不超过二十行，但一个月能省下几个小时。

为什么值得关心：手工重复劳动的最大成本不是时间，而是「注意力税」——每做一次，你就被打断一次。脚本化的意义是让大脑腾出来做真正需要判断的事。

你现在能做什么：本周找一个「你做过三次以上」的操作，用你熟悉的语言写成脚本；不用优雅，能跑就行——跑起来的脚本，好过写得完美的计划。

### 给工具链做「年度体检」：删比装更提效

一个反直觉的建议：每个月末，花十分钟列一份「工具清单」，把超过一个月没打开的工具卸载或归档。工具越多，切换成本越高，认知负担越重——工具链的「负债」和代码负债一样会利滚利。

为什么值得关心：我们总在「加工具」，很少「减工具」。但效率的瓶颈往往不是缺工具，而是工具之间的摩擦：快捷键冲突、数据不互通、两套系统记两遍。

你现在能做什么：现在打开你的应用列表，找出三个「一个月没碰过」的工具；先归档两个，留一个观察——两周后你会惊讶于自己完全没受影响。

## 青春故事会

### 我花三年把工具链调成「自己的形状」

一位开发者分享：三年里他把终端、编辑器、笔记体系一点点改成自己想要的样子——不是追求「最流行」，而是「最顺手」。他的经验是三条：① 每次只改一个地方，用两周验证；② 凡是「每次都要查一下」的操作，都值得写进配置；③ 配置要能解释，半年后你自己还得看得懂。

为什么值得关心：工具链是高度个人化的东西，别人的「最佳实践」不一定适合你。真正有效的打磨，是持续的小步迭代，而不是一次性的「大改造」。

你现在能做什么：挑一个你「每次都用但每次都不顺手」的操作，花半小时查一次配置方案，改掉它；把这半小时当作投资，而不是浪费时间。

### 效率工具上瘾的避坑清单

整理自社区讨论：① 不要在「找工具」上花超过「用工具」的时间；② 新工具先进「试用区」，两周没留下就卸载；③ 警惕「为了用而用」——如果原来的方法更快，就保留原来的；④ 效率工具是为了省时间，不是为了让桌面截图更好看。

为什么值得关心：工具崇拜是一种真实的现代病：我们花大量时间优化「做事的工具」，却忘了真正要优化的是「做事本身」。清单的目的不是反对新工具，而是给「尝鲜」设一个止损线。

你现在能做什么：把这条清单贴到笔记里；下次看到「神器推荐」文章时，先问一句：它解决的是我的问题，还是别人的问题？

## 在看什么

### 一本书：《深度工作》

卡尔·纽波特的《深度工作》讲了一个朴素但反直觉的观点：在注意力碎片化的时代，「长时间专注」本身就是一种稀缺能力，而它可以通过刻意练习重建。放在工具链语境下，它提醒我们：再好的工具，也替代不了「专注地做一件事」的能力。

为什么值得关心：工具解决「做得快」，专注解决「做得好」。这本书适合在刷完一堆工具推荐文章之后读——帮你把「效率」的定义拉回正轨。

### 一个栏目：HN 上的 Ask HN

Ask HN 是 Hacker News 上真实存在的栏目——开发者以「Ask HN:」开头提问，回答区往往藏着比教程更真实的工程经验：从「你用什么做笔记」到「你的构建管线怎么搭」。它不像文章那样精修过，但正因如此，更接近一线实践的真相。

为什么值得关心：别人的踩坑记录，比自己试错便宜得多。每周花二十分钟扫一遍 Ask HN，是性价比很高的「行业情报」获取方式。
